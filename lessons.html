What I know now.

A catalogue of lessons I wish someone had given my 24-year-old self.

The format is borrowed, with admiration, from 37signals.

01

Test location. QA asks the developer:

Your place
or mine?

My recommendation Hide recommendation

Developers. In the app repo, every single time.

  • Solves false positives. Tests change in the same commit as the code, so a red build means a bug, not an intended change.
  • Solves late feedback. You hear about a break on the commit that caused it, not after it reaches the test environment.
  • Shared responsibilities. Developers fix broken tests. QAs test the app and write the missing tests.
  • Gives QAs mental space to actually test the app and write the missing tests, instead of living in maintenance hell.
  • Solves capacity constraints. Maintenance is one of the key challenges as the test count grows. When everyone owns the tests, the burden doesn't fall on a single person.

I have written about this at length in Test Location Matters. It is the single decision that makes or breaks a test automation effort.

Put the tests where the code is. Everything else follows.

02

Test language. QA asks the developer:

Your language
or mine?

My recommendation Hide recommendation

Developers’. The language the app is written in, every single time.

  • Solves ownership. Developers can read, review, and fix a test written in their own language. A test in a language they do not know is a test they will never touch.
  • Solves the two-toolchain problem. One build, one linter, one package manager, one CI job. No second ecosystem to keep alive.
  • Solves duplication. Tests reuse the app’s types, models, fixtures, and clients instead of rebuilding the domain in another language.
  • Solves scale versus maintenance. When tests speak the team’s language, the whole team maintains them, not only QA.
  • Gives QAs a stronger skill. Learning the developers’ language makes you a better engineer, not just a better tester.
  • No need to hire an army of QAs who know a niche, test-only stack. Anyone on the team can contribute a test.

This is why I reach for Playwright in TypeScript on a TypeScript frontend, and RestAssured in Java on a Java backend. The tool follows the language. The language follows the app.

Learn their language. Then the tests belong to everyone.

03

Test level. Where should most tests live? QA asks the developer:

Your level
or mine?

My recommendation Hide recommendation

Developers’. Most tests at unit and integration level. System tests only for what nothing below can see.

  • Most functionality belongs at unit level. Business rules, validations, calculations, edge cases. Every branch of logic, tested in isolation, in milliseconds.
  • Most integration issues belong at component level. Wiring, contracts, serialisation, queries, configuration. Test the seams where two parts meet, with the real parts on both sides.
  • Most system tests are checks that could live lower. They exist because QA cannot see the tests underneath. Read the unit and component tests first. Then write only what is missing.
  • System tests cover only what nothing below can. That the deployed app starts and its pieces are wired together. That one request goes in through the real UI and comes back out with the right data persisted. That login, permissions, and navigation hold across the whole stack.
  • System journeys, not user journeys. A system journey cuts vertically through frontend, middleware, and backend inside your application’s boundary. A user journey runs horizontally across systems you do not control. Stub what sits outside the boundary and cover it with a contract test.
  • Leave the user journey to a human. Automation tells you whether you are building it right. Only a person walking the product tells you whether you are building the right product, and finds the UX issues on the way.
  • Fast and, above all, reliable. A system suite that finishes in minutes and passes whenever nothing is broken. A flaky test is worse than no test: it teaches the team to ignore red.

The system tests I recommend, each walk one system journey end to end: in through the UI, down to the database, and back. Everything else lives one level down, where it runs in seconds and fails for one reason only.

Push every check as low as it can go. What remains is your system suite: small, vertical, fast, and reliable.

04

Test tooling. One cross-platform tool for QA, or the native tool each platform already has? QA asks the developer:

Your tooling
or mine?

My recommendation Hide recommendation

Developers’. Espresso on Android, XCUITest on iOS. Two native tools over one tool in the middle. Every single time.

  • “One tool” is really three. Appium puts a server, a driver, and a client library between your test and the app. Every layer is a place to be slow, to be flaky, and to lag behind the next OS release.
  • Google builds Espresso. Apple builds XCUITest. Dan Cuellar created Appium. And no, it is not the same as Linux or Git. When the company that builds the platform also builds the test tool, the tool knows the platform from the inside. It ships with the OS, it is updated the day the platform changes, and it is not going away.
  • Same repo, same language, same build. The test sits beside the screen it tests, in Kotlin or Swift, and runs with the developers’ build in CI. Lessons 01, 02, and 03 come for free.
  • Developers already know them. Android and iOS developers learn Espresso and XCUITest as part of their craft. Nobody has to learn a WebDriver dialect to help QA.
  • Fast and reliable. In-process, no network hop, no session to set up. Hundreds of native UI tests finish in the time a bridge takes to launch.
  • Yes, you write it twice. Two small, simple, native suites cost less than one large, slow, shared one. And each platform team owns exactly one of them.

Appium’s promise of one test for both iOS and Android is tempting. But one shared test means one outside repo, with the sync problems from lesson 01, and an architecture that trades speed and reliability for portability. Over time it becomes more nuisance than help. Espresso and XCUITest are fast and reliable. Appium is neither. The cost lands on the whole team, every day, for years.

Pick the tool the developer would pick. Then you never test alone.

05

What now?

Start Monday.

  1. Locate Open your test repo. If it is not the application repo, start the move this sprint.
  2. Speak If your tests are in a different language than the app, write the next one in the app’s language.
  3. Level Count your tests per level. If the system layer is the biggest, write the next test one level down.
  4. Tool Before adopting a cross-platform test tool, ask the developers which tool they would use. Use that.

That is it. Learn, share, have fun. If you want to spar on any of these, I offer free 20-minute sessions for the QA community.
